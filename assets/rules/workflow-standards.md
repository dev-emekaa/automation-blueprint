# Workflow Standards

How an automation is designed, on any runtime. The tools are in `tech-stack`; calls to other systems are in `integrations`; AI steps are in `ai-steps`; how code is written is in `coding-standards`. The last two sections give the conventions for n8n and Activepieces.

## Principles

- **Assume every trigger fires twice and every step runs twice.** Webhooks are redelivered, retries re-enter, workers restart. A second run of anything must change nothing.
- **Deterministic first.** A step that rules can decide is code or a node, never a model. AI is for what rules cannot do (`ai-steps`).
- **Side effects are the dangerous part.** They come last in a run, each one recorded, each one keyed, each one reversible or approved.
- **Every run can be reconstructed.** What came in, what each step did, what was sent where, what it cost — from the run record alone.
- **Fail loudly.** A failure alerts someone with enough to act on. Silence is never success; a scheduled run that does not happen alerts too.

## Triggers

| Type | Rules |
| --- | --- |
| **Schedule** | The cron expression and its time zone are explicit. The overlap policy is stated (skip, queue or allow). The catch-up policy after downtime is stated (run once, run each missed slot, or skip). A pause is not downtime: a slot that fires during a pause starts a run that holds itself (Pausing, below), so it is kept for the owner to run or drop, and nothing is caught up on resume. Each run pings the heartbeat; a missing ping alerts. |
| **Webhook** | Verify the caller first (`security` → Inbound endpoints), validate the payload against the trigger contract's schema, respond `2xx` within the caller's timeout — only once the run is started or held; if neither can happen, answer `5xx`, so a caller that retries does — and do the work asynchronously, never inside the request. Deduplicate on the caller's event id. The public URL belongs to the deployment, not the runtime — `https://{hooks domain}/{slug}`, routed by Caddy to whichever build is live — so a caller never changes anything when the version or runtime behind it does. On a vendor-cloud deployment the public URL is the platform's own (or the plan's custom domain), listed in the register, and moving the automation off that cloud means updating its callers (`/automation-convert`). |
| **Polling** | A schedule that reads a cursor (a timestamp or id high-water mark), advanced only after the batch it covers has been processed. The cursor lives in the shared run-record database on every runtime — never in a platform's own static data or a built-in polling node — so a pause holds the batch rather than skipping it, and a conversion finds it where it was. There are two cursors: one for dry runs, and the real one, shared by `real` and `supervised` runs, so starting or ending supervision never moves it; test runs advance neither. A first release's dry run never advances the real cursor; at go-live the owner chooses where it starts — now, or where the dry run began. The interval respects the connection's rate limit. |
| **Event** | From another automation, a queue or a platform event: the same deduplication as a webhook. |
| **Manual** | From the engine dashboard, the platform UI, the console or the CLI, with who ran it and why recorded on the run. Manual runs take the same path as triggered ones. |
| **MCP** *(optional)* | The automation exposed as a tool to an agent: the same authentication and validation as a webhook, and the risk table still decides what may run without a person. |

## Idempotency

- **Every run has an idempotency key**, derived from its trigger — the event id, the schedule slot (`2026-10-26T07:00`), the source record and its version. A run whose key already belongs to a `real` or `supervised` run that **completed successfully** ends as a duplicate, recorded, with no side effects. A key whose run failed, or whose item is in the holding area, can run again — each side effect's own key still stops anything already done from repeating. Dry-run and test runs use their own key prefixes (Dry run, test runs and supervision), so they never make a real run look done.
- **Every side effect has its own key** — the run key, the side effect's id from the spec (its number in Outputs and side effects, never a runtime's step or node name), and the target — taken from the item's fixed identity (the record, the customer, the thread), never from anything a model chose, so a retry or a reprocess derives the same key. Run keys and side-effect keys are derived the same way on every runtime, so another build of the same automation recognises what this one already did.
- **The side-effect record is checked first, on every system, and each key is claimed once.** Before acting, the run checks the record: a recorded result means the side effect is done, and nothing is called; an intent already claimed — by another run, or by an earlier attempt of this one — and not yet resolved means the run holds, never calls. Only once the run's mode, the pause switch and any approval have cleared the side effect does the run claim the key — a unique insert, so two runs can never both claim it — and make the call. The key is also sent to the other system where it accepts one (payment APIs usually do; many messaging APIs, Slack's included, do not), which covers a crash between the call and the record, within that system's key window (Stripe's is at least 24 hours).
- **A write that may have gone out is never repeated blindly.** When a call to a system that takes no key times out, loses its connection or is cut off by a restart, it is not retried: its claimed intent stays unresolved and the item is held — unless the wrapper can look up whether it happened (a sent message, a record by its external id), which then resolves it. A claimed intent older than a keyed system's window is held the same way. A reprocess whose target differs from the one recorded for the same side effect stops for the owner.
- **An unresolved intent is resolved by a person** when no lookup can: from the console or the platform's script, an operator who has checked the other system marks it sent (with the evidence — a message id, a screenshot reference) or not sent (releasing the key), recorded with who and why; then the item can be reprocessed.
- **"Already done" is a success**, not an error: a create that finds its record, a send that finds it sent.

## Steps

- **One purpose per step**, with a typed input and output. A step that needs a paragraph to describe is two steps.
- **Every external call has a timeout.** No call waits forever.
- **Retries are for transient failures only** — timeouts, rate limits, `5xx`, connection resets — and for writes only where the other system accepts an idempotency key or the failure shows the request was never received (Idempotency, above); with exponential backoff and jitter, and a cap from the register's defaults. A `4xx` that is not a rate limit, a validation failure or a refusal is not retried; it fails the item.
- **Rate limits are per connection, shared** by every automation that uses it (Hatchet rate-limit keys in code; batching and wait settings on a platform).
- **Lists are processed in batches** with progress checkpointed, never loaded whole. Pagination follows the API's cursor to the end.
- **Concurrency is keyed by entity** where two runs touching the same record would conflict (one run per customer, per invoice).

## Partial failure

- **Side effects run after everything they depend on has succeeded**, and in an order where an earlier one never needs a later one to make sense.
- **Each side effect is recorded twice:** the intent before the call, the result after, with the other system's id. A crash between the two is found and resolved on the next run, never repeated blindly.
- **A run that writes to several systems states what happens if it stops halfway** — the compensating action for each earlier write (cancel the invoice, delete the draft, post a correction), or why none is needed. It is in the spec's failure policy.
- **Items that fail permanently go to the holding area** — one shared table in the run-record database on every runtime — with the error, the input as its trigger contract defines it, the run key, whether the caller was verified, and the side effects its run already made; and an alert. Each has a reprocess path, on any build of the automation, that runs it again once the cause is fixed: with the same trigger part of the key and the prefix of the new run's mode, so a dry-run item reprocessed for real runs as real. Reprocessing an item whose run already made a side effect is the owner's decision, made from that list.

## Waits and approvals

- **Waits are durable**: Hatchet's sleep and event waits, n8n's Wait node, Activepieces' delay and approval steps. A run waiting for days survives restarts and deploys. Never a sleep in memory.
- **An approval states who approves, through what, what they see, and what happens on timeout.**
  - **Through:** a signed, single-use link in Slack or email; the console's approvals inbox; or the platform's own approval step — only one that shows the action on a page and needs a confirming submit (n8n's Wait or Send-and-wait with a form response, never its Approval response, which approves on a plain link). Activepieces' approval links are plain links, so an Activepieces automation that needs approvals has them through a form that confirms the same way, or is built on n8n or code (`tech-stack` → Choosing a runtime).
  - **They see:** the proposed action exactly as it will be executed — the recipient, the amount, the text — and the inputs that led to it, summarised, never raw personal data they do not need.
  - **On timeout:** do nothing, and alert. An approval never defaults to yes.
  - **After the approval:** the pause switch is checked again before the side effect, so an approval given during a pause is held, not carried out.
- **The decision is recorded** on the run: who, when, approved or rejected, and any edit they made.
- **In a dry run or a test run, no real approver is asked.** The request is recorded as would-have-asked (and sent to a test channel, where the deployment has one), raises no timeout alert, and the run continues as if approved, so the walk and the review show everything after it.
- **In a supervised run, every outward or irreversible side effect needs an approval**, whether or not the spec puts a checkpoint there — through the spec's approval channel, to its approver or, where it names none, a release owner. Each decision — approved as proposed, edited, rejected — is the review of the new version. A rejection or a timeout stops the run before any later side effect and puts the item in the holding area, its key still free, so it can be reprocessed once the version is right.

## Run records

Every run leaves a record that answers what happened without re-running anything:

- the run id, the automation, its version, its mode, the trigger and the idempotency key;
- the input, redacted as `security` says;
- each step: status, start and end, attempts, error, and its output, redacted — enough to replay the run without calling anything;
- each model call and tool call, as `ai-steps` → Observability lists;
- **the side-effect record**: for each effect, the system, the action, the target, the idempotency key, the intent time, the result, and the other system's id;
- the outcome and the run's total cost.

They are the shared core's tables in the deployment's PostgreSQL — on a vendor cloud, a managed PostgreSQL (`tech-stack` → Hosting) — in a database separate from any platform's own. Retention is enforced by the runtime's own cleanup: a scheduled task in code, a scheduled workflow on a platform. Code writes them through the shared run-record module. On n8n and Activepieces the execution log holds the steps, and **every automation, at every risk level**, also writes its run key, outcome and side-effect record to the same tables (through the platform's PostgreSQL node or piece, with a credential granted exactly the shared tables they use — runs, side effects, idempotency keys, the holding area and cursors to write; pauses and live versions to read only — and nothing else), because execution logs are pruned and the keys must outlast them. One record per deployment, whatever the runtime, is also what lets two builds of one automation be reconciled. The same database holds the deploy pipeline's `deploys` table — each automation's live version and its deploy history (`ci-cd` → Packaging). Retention follows the register's defaults.

## Dry run, test runs and supervision

- **Every automation supports a dry run**: the whole run executes, and each side effect is recorded as "would have" instead of performed. It is how cases are walked against real systems' data without touching them.
- **A run's mode is fixed when it starts** and recorded on the run with the build version: `real`, `dry-run`, `test` or `supervised` — a test marker wins, then `dryRun`, then `supervised`. Every side effect and approval reads the run's mode, never the current configuration, so a configuration change — going live, ending supervision — applies only to runs that start after it. A run waiting for days finishes in the mode it started in.
- **A run from an older version holds itself.** Every deploy writes the automation's live version to the `deploys` table just before the new build starts taking runs (`ci-cd` → Deploy, step 4); at its next check, a run whose version differs — a waiting Hatchet run that wakes on new code, or a waiting n8n or Activepieces execution that resumes on the workflow it started with — records itself in the holding area and ends, on every runtime, so a fix or a supervised release reaches it when it is reprocessed on the live build. A waiting approval is asked again there.
- **The dry-run switch** is `dryRun` in the automation's configuration for a deployment: on in development, and on for a first release until go-live. A dry run's idempotency key is prefixed `dry:`, so it never makes the real run for the same item look done. Going live holds the dry-run runs still waiting — Holding what is in flight, limited to `dry-run` runs, as part of the `config` run that turns `dryRun` off — with their full input, and each is reprocessed for real or dropped, as the owner decides.
- **Test runs**: a single run can be marked as a test by its trigger — a manual run started as a test, or a webhook or event carrying the test marker its trigger contract defines, accepted only from an authenticated caller. A test run is always a dry run; its idempotency key is prefixed `test:` and the id of whatever started it (the deploy run, the person), so it never blocks a real run and never repeats an earlier test; it is recorded like any other and left out of the measures. It is how a live deployment is smoke-tested without touching anything, so a test run also passes the pause switch: it makes no side effect either way. Sub-workflows and sub-flows receive the run's mode from their caller and honour it.
- **Shadow mode** is a first release's dry run on live traffic: real triggers, real inputs, no side effects, the would-have actions compared with what a person or the old system did. Required before a first release goes live at `high` risk; the comparison goes in the release record.
- **Supervision** is how a new version of a live automation proves itself on live traffic: it replaces the old version and runs for real, with `supervised` on, so every outward or irreversible side effect waits for a person's approval (Waits and approvals). It is ended by a configuration change once the agreed share of actions has been approved without an edit. Only one build ever acts on a trigger.
- **Correction runs** clean up side effects that already went out (`/automation-fix`): a one-off entry point the fix ships, started by hand, its keys prefixed `correction:` and the issue, every action approved as in a supervised run, and recorded as a correction. With test runs, they pass the pause switch — the only runs with real side effects that do, because each action is approved by a person.

## Configuration

- **What an operator may change without a release lives in configuration**: `dryRun`, `supervised`, schedules, thresholds, recipients, budgets. **What decides the automation's behaviour is part of the build**, versioned and evaluated with it: prompts as files (`ai-steps` → Prompts), and each AI step's model in the automation's `models.json` (code) or on its AI node (n8n, Activepieces). Secrets are separate from both (`security`). Whether it is paused is neither: it is state (Pausing, below).
- **Each deployment's values are committed** in `deploy/{deployment}/config/{slug}.json` — non-secret only — and the deploy pipeline applies them: mounted into the worker (code), or written into the Config node or config step at packaging (n8n, Activepieces). The workflow JSON in `automations/{slug}/` holds the development values. A value is changed by a reviewed PR and the pipeline, never by hand on the server, and every deploy takes the file from the head of `main` — whichever commit supplies the code — so no release, hotfix or rollback can silently undo a go-live or a threshold.
- **Owner-editable settings** — the thresholds or recipients the spec marks as the owner's to change — are the one exception: in code they live in a settings table in the deployment's PostgreSQL, edited through the console, each change recorded with who made it, and read at the start of each run over the file's value.
- **Configuration is validated at start-up** against a schema; a missing or malformed value stops the worker, not the hundredth run.
- **Configuration is expand-only**, like state: a new version may add keys with defaults, and ignores keys it does not know, so a rollback runs with the current file.

## Pausing

- **A pause is a switch, not a deployment change.** Each automation has one row in the run-record database saying whether it is paused, with who paused it, when and why. The console and the deploy pipeline's `pause` and `resume` modes set and clear it; no release, configuration change or rollback touches it.
- **Nothing is stopped or unpublished.** Every run — except test runs and correction runs (Dry run, test runs and supervision) — checks the switch as its first step, and again before every model call, after every approval wait and before every side effect — the inbound route and the first task, `callModel()` and `effect()` in code; the shared guard on a platform. A run that finds its automation paused records its input, and the step it reached, in the holding area and ends. So a webhook, an event or a scheduled slot that arrives during a pause is held, not lost; a waiting run holds itself when it wakes; and a looping automation stops spending at its next check.
- **Resuming clears the switch.** What was held is reprocessed or dropped as the owner decides; nothing held runs on its own.
- **Holding what is in flight** is a separate operation, for when a build is removed (a conversion, a retirement) or a dry run ends at go-live, never needed for a pause: it waits, up to a limit, for running runs to reach their next check and hold themselves; then it lists the automation's queued, waiting and still-running runs, records each one's full input, key and the side effects it already made in the holding area, and cancels them — `holdInFlight(slug, mode?)` in the shared core, and the equivalent script for n8n and Activepieces; given a mode, it holds only runs of that mode. On a platform reached without an API, the release owner does the same from the editor's list of runs, by the release checklist.

## Contracts

- **A trigger's payload is a contract** with whoever calls it: its schema, its signature header and its responses are in the spec, and the runbook has a ready-to-run test call.
- **An output another system or automation depends on is a contract too.** A breaking change to either keeps the old contract working in the new version — it still accepts the old webhook path, and keeps the old output field populated — until every caller named in the spec has moved.

## Money

An automation that moves money is `high` risk always. Amounts are integers in the currency's smallest unit with the currency named; every payment call carries an idempotency key; every payment needs approval unless the spec sets an automatic threshold the owner approved; and refunds and reversals are written in the spec's failure policy before the automation is built.

## Naming

- **Automations:** a verb-led kebab-case slug for what it does (`chase-overdue-invoices`, `triage-support-email`).
- **Steps and nodes:** what the step does, in a few words (`Fetch overdue invoices`, `Draft reminder email`). Names are stable — expressions and run records refer to them.
- **Connections and credentials:** `{System} — {environment}` (`HubSpot — production`).

## n8n conventions

- **One workflow per automation**, with sub-workflows (Execute Workflow) for parts two automations share. A workflow that does not fit on one screen is split.
- **Workflow settings set explicitly:** the time zone, the error workflow, an execution timeout, and which executions are saved. Execution-data pruning is instance-wide, so on a `vps` it is set in the Compose bundle's environment (`EXECUTIONS_DATA_PRUNE` and its age and count limits) from the register's retention; on n8n Cloud the plan's retention applies, and the register records it.
- **One error workflow per deployment** (Error Trigger) that sends the alert with the workflow, the node, the error and a link to the execution.
- **Shared workflows** — the error workflow and sub-workflows two automations use — live in `automations/_shared/n8n/`, one file each, and are released with the deployment's infrastructure (`ci-cd` → Versions and tags). A change to one runs the end-to-end tests of every automation that calls it.
- **A Config node at the start** (a Set node) holds the workflow's configuration — `dryRun`, `supervised`, thresholds, recipients, base URLs — and sets the run's mode from it when the execution starts. The committed values are development's; the deploy pipeline writes each deployment's from its config file (Configuration, above).
- **The guard** is a shared sub-workflow, `automations/_shared/n8n/guard.json`, called right after the caller is verified and the payload validated (Triggers), and before every model and side-effect node: it checks the pause switch (holding the run if paused), holds a run from an older version (Dry run, test runs and supervision), applies the run's mode — would-have for a dry or test run, an approval wait for a supervised one, with a rejection or timeout holding the item and the pause switch checked again after the wait — checks the side-effect record before acting (Idempotency), and writes it. No side-effect node is reached any other way. Where the pinned n8n version does not return correctly from a sub-workflow that waits (setup checks this), the approval wait sits in the calling workflow instead, followed by the guard's pause check, right before the side-effect node.
- **Credentials only through n8n's credential store**, referenced by their `{System} — {environment}` name; never a key in an HTTP node's header or a Code node.
- **Expressions over Code nodes.** A Code node holds a transform no node can express, kept short and commented; logic that needs tests belongs in the code runtime.
- **Every node's `typeVersion` matches the pinned n8n version** in the Compose bundle; the workflow is built and tested against that version.
- **Webhook paths are fixed** and listed in the register; production webhooks use the production URL, never the test URL. On a `vps`, n8n's public webhook URL (`WEBHOOK_URL`) is the hooks domain, so the resume URLs its waits and forms issue (`/webhook-waiting/`, `/form-waiting/`) are on it, routed by Caddy and listed in the register.
- **Inbound webhooks use the generic Webhook node** behind the deployment's `/{slug}` URL, with the sending system's signature checked in the workflow. An app's own trigger node (a Stripe or HubSpot Trigger) registers its own subscription in the vendor's account at the platform's URL, so it is used only where the spec records that subscription as a side effect — created when the workflow is first published, and removed at cut-over and retirement.
- **The production editor is for reading.** The owner sees runs and the flow there; a change to the flow is made in development and reaches production through a PR and a release. An edit made in production anyway is not lost: the deploy pipeline stops before writing over a workflow whose normalised JSON differs, by hash, from what it last wrote, and the edit is exported into a PR first (`/automation-fix`).
- **On a `vps`, every workflow keeps one fixed `id`**, set when it is first built and never changed, so every release writes over the same workflow on every instance, and sub-workflow references and `settings.errorWorkflow` resolve everywhere. **On n8n Cloud**, which cannot create a workflow at a chosen id, workflows are found by name like Activepieces flows: the pipeline creates each through the API on its first release, records the id the instance assigns in the `deploys` table, and rewrites sub-workflow references and `settings.errorWorkflow` from that name-to-id list as it deploys (`ci-cd` → Deploy, step 4). The shared workflows go out first, with the `infra` release, which records their ids the same way.
- **The JSON in the repo is normalised:** instance-specific fields removed (credential ids, `pinData`, `staticData`, `meta.instanceId`), keys in a stable order, unpublished. The deploy pipeline maps credentials by name, writes it over the same id and publishes it (`ci-cd` → Deploy), so the diff in a PR is the change and nothing else.
- **Publishing without a restart.** A publish from n8n's CLI takes effect only after n8n restarts, which interrupts every workflow on the instance; and n8n's REST API cannot create a workflow at a chosen id. So on a `vps` a workflow that does not exist yet on the instance — its first release — is created with the CLI's import, which leaves it unpublished and needs no restart (on n8n Cloud, through the API, as above); every later write, every publish and every removal goes through the REST API, and takes effect at once. The API key has full access except on n8n's Enterprise plan, where its scopes can be limited; it is kept like any other production secret. `/automation-setup` confirms both on the pinned version; where the pinned version can publish only from the CLI, the deploy restarts n8n and the release says so beforehand.
- **Sticky notes** label each section of the canvas with what it does, for the owner who will read it there.

## Activepieces conventions

- **One flow per automation**; shared parts as sub-flows where the version supports them, kept in `automations/_shared/activepieces/` and released with the infrastructure like n8n's.
- **A config step at the start** holds the configuration, the same as n8n's Config node, written per deployment by the deploy pipeline, and **the guard** is a shared sub-flow, `automations/_shared/activepieces/guard`, with the same job as n8n's.
- **Connections only through Activepieces' connection store**, named `{System} — {environment}`.
- **"Continue on failure" is off** unless the spec says a step's failure is acceptable, and then the failure is recorded.
- **Every step's piece version is pinned** in the flow JSON — the instance syncs new piece versions from Activepieces' registry, so the image alone pins nothing. The static checks confirm every step names an exact version, and a piece upgrade is a reviewed change, tested like any other.
- **Flows are found by name**: an Activepieces flow's id is assigned by the instance, so the deploy pipeline finds the flow named `{Name}` in the deployment's project, creates it on the first release, imports the new version over it and publishes it — with an API key, which only Activepieces' Platform and Enterprise editions issue.
- **On the Community edition**, which has no API keys, the pipeline cannot reach the instance: a release owner does the import, publish and production-edit check in the editor, from the release's checklist, and gives the pipeline the flow's id, which its webhook URL contains (`ci-cd` → Deploy).
- **Resume and approval URLs** are on the hooks domain on a `vps`, as on n8n, while the editor stays on its own subdomain: `/automation-setup` confirms how the pinned version sets the base of the URLs it issues for webhooks and resumes, separately from the editor's, and Caddy routes only those paths. Where the version cannot separate them, its waits and approvals are not used, and the automation's approvals run on n8n or code.
- **Inbound webhooks use the Webhook piece's Catch Webhook trigger** behind the deployment's `/{slug}` URL, with the sending system's signature checked in the flow; an app's own webhook trigger only on the terms n8n's conventions give.
- **The exported JSON in the repo is normalised** the same way as n8n's, and the production editor is for reading, as on n8n.
- **Failures alert** through a flow-level error handler or the platform's notification setting, whichever the version provides, to the register's alert channel.
