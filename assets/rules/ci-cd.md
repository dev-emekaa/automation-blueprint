# CI/CD

How a change moves from a pull request to a running automation. The tools are in `tech-stack`; what each test layer proves is in `testing`; the human steps around a release — go-live checks, dry runs, supervision, approvals — are `/automation-deploy`'s.

## Principles

- **Merging does not deploy.** `main` holds reviewed work; production changes only when a release owner runs the deploy for one automation at one version.
- **Each automation is released on its own**, with its own version and tag, so a fix to one never ships another's unreleased change.
- **Production runs exactly what was tested** — the image or workflow JSON built from the tagged commit, never "latest `main`" — with the deployment's configuration as it stands on `main`.
- **AI changes pass their evals before release**, not on every PR.
- **A release is reversible** by redeploying the previous version, and every release says how.
- **Pipelines report; skills write the docs.** No pipeline commits to the repository: results go to the run's summary and artifacts, and the skills copy them into `evals.md`, `releases.md` and the register through their PRs.

## Environments

| | Development | Staging | Production |
| --- | --- | --- | --- |
| **Where** | The developer's machine, from `deploy/local/compose.yml` | A separate deployment of the same kind | The owner's or client's server, or their vendor-cloud account (`tech-stack` → Hosting) |
| **Connections** | Test accounts | Test accounts | Production accounts |
| **Side effects** | Dry run, or test accounts | Test accounts | Real, after go-live |
| **Required for** | Every automation | `high` risk automations where volume makes a mistake costly, as the spec decides | Every live automation |

Most automations need no staging: development on test accounts, then production in dry run or under supervision before unattended side effects, gives the same confidence for less. Where an automation needs staging, every release goes there first and passes its checks before production (`/automation-deploy` → Staging).

## Versions and tags

- **Each automation has `automations/{slug}/VERSION`** — one semver line, created by its first build (a conversion's `next/VERSION` is moved up at the switch-over) and bumped by the PR that prepares its release (`/automation-deploy` Step 2), never by the pipeline. A bump is a change to the value of an existing `VERSION` file; creating one is not.
- **The tag is `{slug}-vX.Y.Z`**, created by the deploy pipeline on the first successful release of that version, on any deployment. It never moves; where the plan has rulesets, a tag ruleset stops `*-v*` tags being moved or deleted. A tag marks the commit; what may be rolled back to is decided by the deploy history on the server, not by tags. The same version going to a second deployment — production after staging — reuses it. Comparing two tags shows exactly what changed in that automation.
- **Infrastructure has its own version**: `deploy/{deployment}/VERSION` and the tag `infra-{deployment}-vX.Y.Z`, for the Compose bundle, the shared workflows in `automations/_shared/`, and the console.

## Packaging

- **Code runtime: one worker image per automation**, built from its folder plus the shared `integrations/`, tagged `{slug}:{version}` and pushed to the repository's GitHub Container Registry; the server pulls with a read-only token. Each service's image tag comes from an environment file on the server that the pipeline writes, so the committed `compose.yml` does not change per release. Each worker runs in its own container with only its own secrets and its config file — a compromised or crashing automation reaches nothing else.
- **Vendor-cloud deployments** have no bundle: `deploy/{deployment}/` holds its `VERSION`, its `README` and `config/`; the pipeline reaches the platform through its API and the run records through the managed database.
- **n8n and Activepieces: one platform instance per deployment**, holding every workflow; each release imports one workflow's JSON, with the deployment's config file written into its Config node or config step.
- **One build acts on each trigger.** A new version replaces the live one; it is never run beside it (`workflow-standards` → Dry run, test runs and supervision).
- **The Compose bundle** in `deploy/{deployment}/` is generated by `/automation-deploy` and committed: `compose.yml`, `.env.example`, the Caddyfile and Caddy's build file, `config/`, the backup script, and its README. The console, when used, is built as an image here and released with the infrastructure.
- **Routing** (`vps`): the committed Caddyfile imports one route file per automation from a directory on the server, which the deploy pipeline writes — the public path `/{slug}` to the live build's internal address. Switching builds is one route file and one Caddy reload. The hooks domain also routes n8n's and Activepieces' resume paths to the platform. Each route waits for its upstream while a worker or platform restarts (Caddy's `lb_try_duration`, a few seconds); `/automation-setup` confirms on the pinned Caddy that a request with a body is retried, and the spec lists any caller that never retries.
- **What is live, and the deploy history**: the deploy pipeline keeps a `deploys` table in the deployment's run-record database — on every kind of deployment, and backed up with it — recording each automation's live version and commit, the hotfixes it contains, the hash of the normalised workflow it last wrote (n8n, and Activepieces with an API key) the instance-assigned ids of its workflows (n8n Cloud, Activepieces) — and the history of every version it has deployed there, with its commit and date. Every mode that deploys writes it (`workflow-standards` → Dry run, test runs and supervision); `config`, `rollback` and the production-edit check read it, so a configuration change after a rollback applies to the version actually running, and a rollback can only go to a version this deployment has run.

## Pipelines

| Pipeline | Trigger | What it does |
| --- | --- | --- |
| **1. PR checks** | Every PR to `main` or a `hotfix/*` branch; every push to `main` and `hotfix/*` | Static, unit, step and end-to-end tests for every automation the change touches, and for every automation using a wrapper or shared workflow it touches; dependency audit; secret scan |
| **2. Release gate** | Manual, or called by Pipeline 3 | Evals for an automation whose prompts, models, schemas or AI steps changed since its last tag; integration tests for wrappers or connections that changed — with the model keys from the protected `release` environment and the test-account credentials from `test` |
| **3. Deploy** | Manual — release owners only | Releases, reconfigures, rolls back, pauses, resumes or retires one automation on one deployment, or releases one infrastructure version |

### 1. PR checks

**Required to merge.** Target: under ten minutes. The run on a push to `main` or `hotfix/*` checks the squash-merged commit itself, which is the commit a release deploys.

1. Install from the lockfile, cached.
2. Static checks, unit, step and end-to-end tests for the affected automations. End-to-end tests for n8n and Activepieces start the pinned platform as a service container and run the cases against it, with test-account credentials from the `test` environment — on PRs from this repository only, never from forks.
3. Dependency audit and secret scan.
4. For a PR that bumps a `VERSION` (Versions and tags, above): the release notes entry in `releases.md` exists.

### 2. Release gate

Runs the evals and integration tests the release needs, and fails if any threshold is missed. A run with nothing to gate passes and says so. The scores, failures, cost and latency go to the run's summary and an artifact; `/ai-evals` or `/automation-deploy` records them in `evals.md`.

### 3. Deploy

**Trigger:** GitHub → Actions → Deploy → Run workflow. Only release owners can run it; running it is the approval. Inputs: the automation (or `infra`), the deployment, the commit that supplies the code (defaults to the head of `main`; a SHA deploys exactly that commit; branch names are rejected), and the mode. **The configuration always comes from the head of `main`**, whatever the commit, so a hotfix or rollback never brings back an old `dryRun`, `supervised` or threshold. The pause switch is never touched by `release`, `config` or `rollback`.

| Mode | Does | Tags |
| --- | --- | --- |
| `release` *(default)* | Deploys the commit's version as the live build, replacing the one before it | `{slug}-vX.Y.Z`, unless it exists |
| `config` | Applies `deploy/{deployment}/config/{slug}.json` to the live build at its live version — go-live, starting or ending supervision, a threshold. When `dryRun` goes from on to off, it then holds the dry-run runs still waiting (`workflow-standards` → Pausing, limited to `dry-run`) | — |
| `rollback` | Redeploys a version from this deployment's deploy history (a further input) as the live build | — |
| `pause` · `resume` | Sets or clears the automation's pause switch (`workflow-standards` → Pausing), with the reason; nothing is redeployed: step 1, then the switch is written to the run-record database (step 4 does only that), then steps 5 and 6 | — |
| `retire` | For a paused automation: holds what is in flight, then stops and removes its worker service or unpublishes and deletes its workflow, and removes its route; steps 1 and 6 run, and of step 4 only the backup and the removal | — |

1. **Check**:
   - **Every mode**: the actor is a release owner.
   - **`release`**: the commit is on `main` or a `hotfix/*` branch (`git merge-base --is-ancestor`), and Pipeline 1 passed on it. Its `VERSION` is higher than the automation's last tag, or equal to it with that tag on this commit; a hotfix commit's is higher than the tag its branch was cut from, which must be the version live on production (staging may go down to it). A commit on `main` contains the `main`-side fix of every hotfix the live version has — each hotfix's release entry names its `main` PR, whose merge commit must be an ancestor — so a release never undoes a hotfix.
   - **`rollback`**: the version is in this deployment's deploy history; the commit's branch does not matter, since a hotfix branch is deleted once merged.
   - **`retire`, and a `release` or `rollback` that changes the runtime**: the automation is paused.
   - **n8n, and Activepieces with an API key**: for `release`, `config` and `rollback`, the live workflow's hash matches the one last written; if it was edited in production, stop — the edit goes into a PR first (`workflow-standards` → n8n conventions). For `pause`, `resume` and `retire`, which must work whatever state the workflow is in, a mismatch is reported but does not stop the run; a `pause` on an edited workflow still sets the switch, then fails and says to unpublish the workflow at once, since an edit made in production may bypass the guard.
2. **Gate**: for `release`, run Pipeline 2 for this automation. A failed gate stops here.
3. **Package**: build and push the worker image (code), or normalise the workflow JSON and write the deployment's config into it (n8n, Activepieces). `rollback` uses that version's artifact; `config` the live version's, from the record of what is live.
4. **Deploy.** On a `vps`, over SSH with a deploy key limited to it; on a vendor cloud, through the platform's API over HTTPS with the key from the deployment's environment, and the managed database over TLS — with no SSH, bundle or route files, and the platform's own URL in place of a route. Back up the database (a managed database's snapshot on a vendor cloud); apply state migrations (expand-only — `workflow-standards` and the coding standards say how); then:
   - **The live version** (`release`, `rollback`): written to the `deploys` table just before the new build starts taking runs — before the service starts, the workflow is published or the route switches; on the manual import path, before the run stops for import — so runs from the version being replaced hold themselves, and the new build's own runs, the smoke check's included, do not.
   - **Code:** write the image tag, `docker compose pull` and `up -d` for the automation's service — the first `release` of a code automation is what starts its service. A `config` run recreates the service (`--force-recreate`), since a worker reads its configuration at start-up.
   - **n8n:** map credentials by name; on a `vps`, create the workflow at its fixed id if it does not exist yet; on n8n Cloud, find it by name, create it through the API if it does not exist and record its id, then rewrite its sub-workflow and error-workflow references from the name-to-id list in the `deploys` table (`workflow-standards` → n8n conventions); then write it, and publish it, the way setup confirmed for the pinned version (Publishing without a restart).
   - **Activepieces, with an API key** (Platform or Enterprise): the production-edit check, then find the flow by name (create it on the first release), import the new version over it, and publish it.
   - **Activepieces Community, or a vendor-cloud plan without the API**: the run publishes the packaged flow or workflow as an artifact and stops, marked as waiting for import. A release owner checks in the editor that the live flow is unchanged since the last release, imports and publishes the new one from the release's checklist, then runs the deploy again with the same commit, `imported: true`, the id of the run that stopped (which must have passed the gate, where its mode has one) and the flow's id (from its webhook URL), which skips the gate and the import, records the id, writes the route to that flow on a `vps`, and goes on to the smoke check. `config` and `retire` take the same manual path from the run's checklist: the release owner writes the config step's values in the editor; or, to retire, unpublishes the flow, holds each run still waiting from the editor's list of runs (`workflow-standards` → Pausing), and deletes the flow only once none is waiting; then confirms with the second run.
   - **Routing** (`vps`): write the automation's route file for the live build and reload Caddy.
   - **A conversion's release** — a `release`, or a `rollback`, whose runtime differs from the live build's — runs only while the automation is paused (`/automation-convert` Step 4): it holds the old build's in-flight runs (`workflow-standards` → Pausing), deploys and publishes the new build (starting its service, for code), creates the vendor subscriptions the spec records for an app trigger on the new build and removes the old build's, and switches the route; the old build's workflow or service is removed only after the smoke check passes — its test run passes the pause switch, so it runs the new build end to end even while paused — so a failed switch rolls back by pointing the route at the old build again. **A conversion that moves to another deployment** (onto or off a vendor cloud) is a `release` on the new deployment and a `retire` on the old one, both while paused. The automation's rows — the pause switch (still on), cursors, idempotency keys and side-effect records within retention, and the holding area — are copied to the new deployment's run-record database before the release, with the counts checked; after the old deployment's in-flight runs are held and its callers repointed, the rows added there since are copied again and checked, before anything resumes (`/automation-convert` Step 4). Rolling a conversion back is a conversion back: the old build's service, where it is code, is first restored to the bundle by a PR (`/automation-convert` → Undoing a conversion).
5. **Smoke check**: the trigger answers, connections authenticate, the running worker reports the hash of the config file just applied (code), a test run of one case runs every step the case expects (`workflow-standards` → Dry run, test runs and supervision), the alert path fires. Test runs pass the pause switch (`workflow-standards` → Dry run, test runs and supervision), so this holds for a paused automation too.
6. **On success**: `release` creates the tag if it does not exist; every mode records itself in the deploy history (the live version itself was written in step 4, just before the new build started taking runs, and is put back if the release is rolled back); every mode writes its summary — what was deployed, where, the gate's results, the smoke check. **On failure**, by mode: `release` and `rollback` roll back to the version before (below) — or, for a first release, which has nothing to roll back to, unpublish the workflow or stop the service and remove its route; `config`, `pause`, `resume` and `retire` stop and alert, leave the live build as it is, and never redeploy — a failed `pause` says to unpublish the workflow or stop the service at once.

Going live — leaving dry run for real side effects — and ending supervision are `config` runs on PRs `/automation-deploy` prepares after its checks and the owner's approval.

`infra` deploys a deployment's infrastructure at the commit. On a vendor cloud that is the managed database's migrations and its restricted role, and the shared workflows through the platform's API; it also confirms the platform version the cloud now runs against the one the tests use. On a `vps` it is the bundle: the Caddy build, the infrastructure services in `compose.yml` and their images, the shared core's migrations and the restricted database role platform automations use, with exactly the grants `workflow-standards` → Run records lists, the shared workflows, the console; health checks green; tag `infra-{deployment}-vX.Y.Z`. It never starts or removes an automation's worker service: its `release` starts it, and a conversion's `release` or `retire` removes it.

## Hotfixes

`main` may hold unreleased changes to the same automation, so a fix for the live version cannot simply ride `main`.

1. Branch `hotfix/{slug}-vX.Y.Z` from the live tag. The fix arrives on it by a PR, reviewed like one to `main`, and `/automation-deploy` Step 2's PR to the same branch adds the patch bump and the release entry; the same fix goes to `main` through a normal PR.
2. The merge runs Pipeline 1 on the branch; Pipeline 3 is run with its commit, and the configuration still comes from `main`.
3. The branch is deleted once the fix is live and on `main`.

## Rollback

| Situation | How |
| --- | --- |
| **An automation misbehaves after a release** | Pipeline 3 in `rollback` mode with the previous version. State migrations and configuration are expand-only, so the old version runs against both; `/automation-deploy` → Rollback then asks whether the current configuration — supervision, dry run — still fits |
| **Side effects already went out** | The runbook's reversal steps, from the side-effect record — decided with the owner (`/automation-fix`) |
| **Stop everything now** | Pause the automation — from the console, or Pipeline 3 in `pause` mode. Every run holds itself at its next check (`workflow-standards` → Pausing) |
| **Infrastructure change breaks the server** | Redeploy the previous infrastructure tag; restore the database from the pre-deploy backup only if a migration cannot be undone forward |

## Repository rules

- `main` and `hotfix/*` are protected: PRs only, Pipeline 1 required, one approving review where there is more than one developer; a ruleset lets only release owners create `hotfix/*` branches.
- Squash merges, so each commit on them is one reviewed PR.
- **GitHub environments**: `test` holds the test-account credentials; `release` the model keys for evals; and one environment per deployment, `deploy-{deployment}` (staging included), its server address, SSH host key and deploy key — or, for a vendor cloud, the platform's URL and API key and the managed database's migration credential. `release` and every `deploy-*` environment deploy only from `main` and `hotfix/*`, and Pipeline 3's own check holds the commit to the same branches.
- **Plan limits**: on a private repository, environments — their secrets and branch rules — rulesets and branch protection need GitHub Pro, Team or Enterprise. Without them the values must be repository secrets, which anyone with write access can read through a workflow on their own branch; so only release owners have write access and everyone else contributes through forks, or the repository moves to a plan with environments. The infra guide says which applies.
- Dependabot PRs go through Pipeline 1 like any other; an image or platform version bump also runs the end-to-end tests of every automation on that platform.
